## 下一步建议

先形成 I3 手工日计划的可实施规格，再按确定的边界交付代码。依据 `identity-registration-and-access.md`，I3 涵盖创建、读取、编辑、内容可空、同班同日唯一、版本冲突、权限和同事务更新登记；不能直接把整份“手工日计划到周计划确认与 Word 导出”规格当作本轮实现范围。

I2 已完成，证据以 `i2-implementation-status.md` 为准。当前工作区有大量未提交的 I2 文件和更早的文档修改，不能清理、回退或把所有差异算作新任务产出。路线文档中的“I2 待实现”和“pi 优先”已经过时，下一轮应定点更新，保留历史验证范围。

必须先收口的事项：

- 内容 schema：完整覆盖已确认栏目、稳定游戏组与游戏身份、共用内容、版本关系，区分手工内容和不存在的 AI 拆分基准。
- 更新登记：明确尚无周计划与已有周计划的语义、真实持久状态及未来消费契约。ADR 0002 要求同事务登记，不能以没有工作进程为由省略，也不能创建没有实际用途的任务占位表。如果 I3 边界不足以履约，应提出最小范围调整及其影响，由用户决定，不能暗中扩大。
- I2 联动：首次创建日计划与 `school_settings.plans_started_at` 同事务，沿用兼容的锁顺序，阻止配置确认和首次创建之间的竞态；删除全部计划不能清空标记。
- 产品未决项：历史表头采用快照还是随资料变化；删除／恢复是否纳入本次 I3，以及恢复冲突的可执行流程。先核对现有决定，只向用户提交确实未决定、影响本轮的数据或交互问题。

## main 与 OpenCode 的协作方式

1. **规格先行。** main 下发上述任务；OpenCode 交付文档和问题清单。main 核对关键契约及新增产品歧义，再集中提交用户决定，避免把普通技术选型都变成问题。
2. **单一写入者。** 实施获授权后，OpenCode 独占当片业务代码、迁移和测试；main 做只读审查、资源协调、直接相关检查及验证报告。双方不同时编辑同一文件，main 不另起业务实现。
3. **每次一个能检查的结果。** 每片交接写明目标、允许文件、既有接口、禁止范围、验收命令和停止条件。初步顺序为数据与事务核心、API 权限和冲突、前端闭环；更新登记和阶段标记随核心保存同步落地，不能拖到最后补。
4. **用证据反馈。** main 反馈具体请求、错误、数据库状态或文件位置；OpenCode 定点修复。日志保留真实退出码，跳过不算通过；不要用 tail 等管道的退出码替代原命令结果。维护“检查—代码版本／输入—结果”记录，无相关变化不重跑。
5. **资源和秘密由 main 控制。** 数据库准备、迁移和依赖操作先按用户授权核对具体资源。不得输出 DSN、环境文件、密码或完整环境变量；OpenCode 只获得任务必需的脱敏配置及已批准命令。共享数据库上的清理测试串行，浏览器验证与清库测试隔离。
6. **有限上下文交接。** 沿用本地 OpenCode 已配置模型；正常结束一片后再派下一片。会话膨胀或损坏时用简短事实交接开新会话，不无限重试，也不切回 pi。每片报告实际交付、检查及未完成项，main 据此推进，不能仅凭“完成”叙述判定交付。

本轮仅新增本文，未调用 OpenCode、未运行测试、未更改业务实现，也未更新路线文档；路线更新是上述下一轮提示词的明确任务。
