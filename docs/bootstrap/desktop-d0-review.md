## 2. 首轮发现与依据（当前状态见 §7）

以下行号对应本轮工作区；修复后以符号和行为定位，不要求保留行号。P1 为高优先级阻断，P2 为本切片需修复的正确性／验证问题。

### R1 · P1：无控制台目录包无法正常初始化

位置：[d0_main.py:84](../../desktop/d0_main.py#L84) `ServiceRun.__init__`，配套 [build_d0.py:57](../../desktop/build_d0.py#L57)。构建使用 `--windowed`，Uvicorn 配置仍采用默认日志 formatter。当前依赖在无控制台的 `sys.stdout=None` 条件下执行 `.isatty()`，报 `ValueError: Unable to configure formatter 'default'`，底层是 `AttributeError: 'NoneType' object has no attribute 'isatty'`。

本轮复制现有包至仓外、不重定向输出执行 `--selftest`，进程停在“D0 自检启动失败”错误窗口，未生成结果；将源码的标准输出／错误设为 `None` 后构造相同配置，独立复现上述异常。交互入口与自检共用这段初始化，教师普通启动同样受影响。需要适配无控制台日志，并保证初始化／启动失败时释放已经创建的 SQLite 引擎和服务资源。验收必须包含无控制台、无重定向的普通包启动，不能只从终端重定向运行。

### R2 · P1：Word 保存失败会损坏原文件或留下半成品

位置：[d0_host_api.py:61](../../desktop/d0_host_api.py#L61) `write_docx_file`。函数先 `open(path, "wb")` 截断目标，再写入、flush 和 fsync。隔离复现中，真实打开临时目标后写入 3 字节再抛 `OSError`：接口返回 `failed`，原目标已变成 `b'PK-'`；新目标也留下半成品。另注入 fsync 失败，返回失败时旧内容也已覆盖。现有占用测试只验证打开之前失败，未覆盖该分支。

按 D0-6，应先在目标同目录写临时文件，完整写入、刷新和必要校验成功后再原子替换；失败保护原目标并清理本次临时文件。补部分写入、flush/fsync、替换失败及成功重试测试，不能把“显示失败”当成文件保护已通过。

### R3 · P2：当前前端类型检查失败

位置：[helpers.ts:107](../../frontend/src/d0/helpers.ts#L107) `triggerUiSave`。返回对象增加 `messageText`、`checkboxNow`，但返回类型未声明这些字段。实跑 `npm run typecheck` 返回 TS2353、退出码 1，与实施报告“通过”不一致。修正类型／调试字段后，在最终源码上重新执行检查、构建和打包，不能以旧前端产物替代当前源码验证。

### R4 · P2：Windows 默认完整构建命令不可执行

位置：[build_d0.py:34](../../desktop/build_d0.py#L34) `build_frontend`。原生 Python 通过 `subprocess.run(["npm", ...])`／`["npx", ...]` 调用 Windows 脚本入口，本机两者均复现 `FileNotFoundError [WinError 2]`；同环境 `npm.cmd --version`、`npx.cmd --version` 均成功返回 `11.19.1`。手工 PowerShell 构建或 `--package-only` 不覆盖默认完整入口。

应解析适合 Windows 的工具入口并提供缺失提示，实际复跑默认完整构建；顺带修正已声明却未生效的 `--skip-frontend` 参数。报告中的安装命令还应使用现有 `requirements-d0.lock.txt`，目前只从宽泛 requirements 安装，不能复现记录的依赖集合。无需扩大为全环境审计或新增依赖选型。

### R5 · P2：数据库写入失败后丢失待重试的输入

位置：[App.vue:68](../../frontend/src/d0/App.vue#L68) `saveState` 失败分支、[App.vue:49](../../frontend/src/d0/App.vue#L49) `readState`。先保存 A，再编辑为 B 并模拟写入失败，失败分支读取旧记录并将输入框恢复为 A；关闭模拟后重试保存的是 A，B 已丢失。应区分已保存状态与编辑输入，失败保留 B，数据库仍为 A；修复时也避免保存飞行期间的新输入被读回值覆盖。现有驱动在失败步骤没有输入不同内容，未检测到此问题。

### R6 · P2：宿主桥初始化存在就绪竞态

位置：[App.vue:140](../../frontend/src/d0/App.vue#L140) `waitHostApi`、[helpers.ts:55](../../frontend/src/d0/helpers.ts#L55) `collectSession`。前者仅等待 `window.pywebview` 存在，后者在 `api` 对象存在后立即调用 `get_session`。本机 pywebview 6.2.1 的 `webview/js/api.js` 先建立 `api: {}`，`webview/util.py` 分次注入，随后才注册函数并触发 `pywebviewready`。若页面落在这个间隙，会调用未定义的函数；`onMounted` 无异常收口，页面不能建立会话。

应等待所需桥函数实际可用或可靠的就绪事件，处理已经就绪的情况，并给出超时／拒绝的明确反馈。补延迟桥注入验证，不靠延长固定睡眠消除竞态。本轮重定向包运行的 `page_ready=false` 原因尚未定位，不能直接认定就是此竞态。

### R7 · P2：人工保存目标未落实 DOCX 后缀限制

位置：[d0_host_api.py:54](../../desktop/d0_host_api.py#L54)、[d0_host_api.py:143](../../desktop/d0_host_api.py#L143)。`suffix_ok` 只记录结果，不阻止写入；人工对话框分支不像自动路径分支那样校验后缀。隔离模拟对话框返回 `unexpected.txt`，实际创建文件并返回 `saved, suffix_ok=false`。原生对话框的文件类型过滤不等于应用侧校验。

应在统一落盘边界、创建任何文件之前约束最终目标为 DOCX，覆盖人工和自动路径；验证大小写、无后缀、其他后缀的明确处理。不得将受限接口扩成任意文件写入桥。

### R8 · P2：合法的每用户 WebView2 安装被误判缺失

位置：[d0_main.py:50](../../desktop/d0_main.py#L50) `webview2_runtime_version`。检测对 HKLM、HKCU 均使用 `SOFTWARE\WOW6432Node\...`，而每用户安装位于 HKCU 的 `SOFTWARE\Microsoft\EdgeUpdate\Clients`；当前 pywebview 的 `platforms/winforms.py` 也区分这两者。隔离提供合法 HKCU 安装记录时，本函数返回 `None`，交互入口拒绝启动。

按注册表 hive／体系结构正确检测，补系统安装、每用户安装及真实缺失三类测试。测试不得安装／卸载系统组件或修改真实注册表。

### R9 · P2：诊断脚本将原始启动令牌写入文件

位置：[d0_jsdiag.py:35](../../desktop/d0_jsdiag.py#L35) 至保存诊断结果的逻辑。脚本将 `get_session()` 的原始返回值加入 `lines`，再写入 `build/desktop-d0/jsdiag.json`。本轮仅检查字段存在，确认现有诊断文件包含 `launch_token`，未读取或展示令牌值。这违反 D0“令牌不进入日志”的明确要求。

改为只记录布尔就绪／成功状态；在保留非敏感故障证据的前提下脱敏这份已知诊断产物，检查同一 D0 诊断路径是否还有泄漏，不扫描无关私密配置。报告不再笼统宣称所有诊断日志无令牌。

### R10 · P2：自检可误报成功，不能证明完整重启与导出链路

位置：[d0_driver.py:163](../../desktop/d0_driver.py#L163) 总结条件，以及 `drive_window` 的状态读取和 Word 步骤。隔离模拟返回“无会话读取 200、保存成功提示为 false、版本维持旧值”，仍得到 `ok=true`：现有总结未强制检查这些条件。启动后的首次 API 状态读取又位于保存之后，不能独立证明重启前内容被读回。

Word 步骤实际由 Python 直接生成字节，然后调用自动路径宿主保存，绕过页面按钮、`exportWord` 和 `/api/probe/export`。这能证明部分生成／桥写能力，不能称实际页面导出链路通过。应让每项必需断言进入总体结果，失败或超时返回非零；记录启动后、写入前的旧内容与版本，跨两个完整进程验证；导出从真实页面入口经过 API 到宿主，自动授权最多替代选路径这一步。人工对话框成功、取消、失败重试仍单独验证。

### 6.2 剩余可行动问题

**R10 · P2：自检仍会接受保存成功但版本未递增。** 当前 [d0_driver.py:263](../../desktop/d0_driver.py#L263) 的重试断言只比较内容，独立数据库读取也只比较内容；首次保存 [d0_driver.py:213](../../desktop/d0_driver.py#L213) 只检查版本至少为 1。隔离模拟旧 `A/v5`、失败保持 `A/v5`、重试返回 `B/v5`，得到 `overall_ok=true`、`failed_checks=[]`。这是自检可信度问题，不是本轮发现真实 SQLite 版本错误；本轮正向运行实际为 A/v1→B/v2。

修复应在每次成功保存核对 `new_version = old_version + 1`（空库首次为 1），同时检查 API 和独立数据库内容／版本一致。新增直接驱动 `drive_window` 的负向回归，拒绝“内容正确但版本不变／错误”和“API 与数据库版本不一致”；仅测试 `combine_ok` 对布尔值取 AND 不能覆盖断言缺失。

**R10 的异常终止补项。** [d0_main.py:380](../../desktop/d0_main.py#L380) 捕获驱动异常后仅写 `summary`，未关闭自检窗口；`webview.start()` 仍等待 GUI 结束，可能直到真人关窗才写摘要并返回非零。隔离注入异常确认未调用窗口关闭。应让异常自检在有限时间内关闭本轮窗口、停止服务、释放探针、写失败摘要并返回非零。该问题影响异常自检，不宣称正常交互流程失效。

**R1 的清理补项（低风险，不新增产品阻塞）。** [d0_main.py:294](../../desktop/d0_main.py#L294)、[d0_main.py:352](../../desktop/d0_main.py#L352) 在 `start_and_wait()` 超时失败后直接返回，未调用 `service.stop()`。隔离真实 Uvicorn 延迟 startup 可在函数返回后继续启动；正常主程序最终退出会销毁 daemon，因此不据此宣称完整进程退出后仍遗留服务。应统一失败路径清理，交互错误框出现前结束本轮服务，避免错误模态停留期间后台继续启动。
