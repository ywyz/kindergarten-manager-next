## F1 — P1：按 no_plan 清空列会丢弃已经确认的人工内容

位置：`docs/specs/word-export-implementation.md:218`（§5.2）。

规格同一行既要求读取 `effective`，又规定 `plan_state=no_plan` 时“列空”。I4 §2.4 已允许负责人覆盖确定性栏目；`backend/app/services/weekly_plan_content.py:269` 至 `:299` 的实际构造逻辑在无日计划时保持 source 为 null，但仍将非 null 的 override 派生到 effective。I4 规格 `manual-weekly-plan-confirmation.md:223` 至 `:226` 明确了这三层关系。

可触发场景：某上课日没有日计划，负责人在周计划中填写该日晨间谈话或集体活动，确认不完整版本后导出。若照“no_plan 列空”实现，会丢掉确认快照中真实存在的人工文本。

修订要求：教学日栏目按所选确认快照的 effective 输出；no_plan 描述来源缺失，不是清空 effective 的条件。只有 effective 本身为空才留空。保留缺来源事实，不伪造日计划，也不在导出时重新派生内容。

必要案例：no_plan + 非空 override、no_plan + 空 effective、saved + 显式空字符串 override；均逐字段保留已确认结果。

## F2 — P2：学期周号不能作为跨学期排序键

位置：`docs/specs/word-export-implementation.md:182`（§4.2）。

“按 week_number（= 周起始日）升序”不成立。周号是学期内序数，后一学期第 1 周可能被排在前一学期第 18 周之前。范围 API 未限定只能查询一个学期，§10.2 也包含跨学期场景。

修订要求：按 `week_anchor(term.start_date) + 7 * (week_number - 1) 天` 得到实际周起始日期后升序；必要时加稳定次级键。按计划身份去重，不能按裸 week_number 去重。沿用已有日历函数，不另造周次算法。

必要案例：前学期末周与后学期首周同时命中范围；验证日期升序、整周不裁切、不同学期相同周号不被错误合并。

## F3 — P2：必需更新提示缺少完整的服务端判定规则

位置：`docs/specs/word-export-implementation.md:165`（§3.6），及 §4.2 对读取用途的约束。

现有 `weekly_plan_read_service.py:374` 的 `_list_confirmation_state()` 仅比较当前确认行的 draft_version 与当前草稿版本；`_live_context()` 在 `:165` 起另行计算 projection_pending。来源发生变化但尚未刷新时，needs_confirm 可以仍为 false。另一个场景是显式导出历史确认 V1，而当前确认 V2 与当前草稿一致，当前 needs_confirm 同样不能代表所选 V1 的新旧。

Contract 已要求更新等待时导出上一确认版必须提示（`docs/modules/weekly-plans.md:52`）；最小规格也明确“已确认 V1 后日计划保存 V2”应提示未更新（`manual-plans-and-word-export.md:153`）。这部分无需重新向用户询问是否提示。

修订要求：服务端围绕实际选中的确认行，分别定义历史确认、草稿领先、来源待更新/过期等事实的判定与提示。明确允许为警示读取新旧状态元数据，但不能将实时来源、草稿或投影混入 Word 正文；既有 freshness helper 若计算的是当前草稿，不能不加区分地用来判断历史确认行。前端布尔值只能辅助展示。成功响应必须有可靠的提示承载方式，不能因 §7 将某个响应头写为“可选”而省略产品提示。

必要案例：当前确认且无更新、草稿领先、仅来源更新、显式历史确认、已确认但保留 stale facts。后者需按既有语义说明，不能将“已确认”解释为“来源一定最新”。

## D1：日计划缺项确认的跨请求语义未决

位置：I5 §3.3、§3.5（`:145`、`:159`）。

单次请求内钉住版本能防止生成时混读，但不能消除“409 提示 → 用户确认 → 重试”两个请求之间的变化。例：第一次提示缺活动目标，期间另一人保存新版本并清空活动过程；重试只带 ack_missing=true，重新计算缺项并不能证明用户看过新出现的缺项。

既有 Contract 没有明确选择：确认是否宽泛适用于重试时的最新内容，还是绑定用户看过的版本/缺项集合。因此应撤回“无预检-下载竞态”的无条件表述，并将这项列为片 1 相关逻辑定型前的产品决定。

候选：A，明确告诉用户确认针对重试时当前内容及其全部缺项；B，绑定已展示的版本/事实，发生相关变化时重新提示。建议优先评估 B，以保留确认对象的一致性；具体令牌、指纹或版本清单是后续工程设计，不能在本次审核中视为已确认。无论选哪种，权限必须每次重判，客户端提交的 facts 都不能成为权威。

## D2：确认后日历变化时，布局和内容的时间语义需核实

位置：I5 §4.2、§5.2、§5.3（`:181`、`:218`、`:229`）。

I5 选择“当前有效日历决定动态列/表头，内容来自旧确认快照”；Contract 规定依据有效日历、保留确认版本，但尚不足以唯一确定所有日历变更后的导出行为。例如已确认周日教学内容后，该周日改为休息日，按当前日历列集合会删去周日列；反过来新增教学日时，旧快照可能仍标记 rest。正文逐字段保留、假期标识和动态列之间需要明确如何协调。

先查既有已确认依据。若不能推出唯一答案，将“布局用确认时日历还是导出时当前日历，以及增删教学日如何处理旧确认内容”列为待确认项；不得把 I5 自己的工程提案循环引用为已确认产品事实，也不得顺手增加确认 schema 字段或迁移。

与此分开，**同一次导出读取中的范围、版本、日历修订、列和表头必须使用一致性视图**，这是工程要求，可直接补入规格。纯 mock 单测只能证明组织逻辑；真实 MySQL 隔离行为留给原定集成层，不冒充已经验证。
