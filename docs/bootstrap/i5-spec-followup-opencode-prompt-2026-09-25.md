### 1. 修复 no_plan 导致人工已确认内容丢失

I5 §5.2 的“plan_state=no_plan 列空”与 I4 的 effective = 非 null override 优先，否则 source 相冲突。无日计划不代表负责人没有在周计划中填写并确认内容。

- 教学日的导出文本读取所选确认快照的 effective。
- no_plan 仅表示缺日计划来源，不得用它清空非空 effective。
- effective 本身为空才留空；保留来源缺失事实，不伪造来源、不重算快照。
- 在验证矩阵增加 no_plan + 非空 override、no_plan + 空 effective、saved + 显式空字符串 override 的预期；确认已保存的人工文本不丢失，空值不被自动补回。
- 休息日/日历发生变更的布局问题按第 5 项处理，不能借此擅自决定。

### 2. 修复跨学期排序与去重键

- 删除 week_number 等于周起始日的表述。
- 按既有 week_anchor(term.start_date) 加 7 × (week_number - 1) 天得到实际周起始日期，再升序；必要时给稳定次级键。
- 按计划身份去重，不按裸 week_number 去重；不改变严格范围、教学日相交选整周、不裁切的规则。
- 增加跨学期末周/首周、不同学期相同周号的案例，写清预期顺序及不误合并。

### 3. 明确服务端“未包含最新变化”提示

- 判定围绕本次实际导出的确认行，不能只用当前 needs_confirm。
- 分别覆盖：当前确认无变化、当前草稿领先、仅日计划来源变化尚未刷新、显式导出历史确认版本、确认时已记录未更新来源。
- 现有 Contract 已要求“日计划保存 V2 后导出确认 V1”提示未更新，不把这个已确认行为重新列为产品问题。
- 核对现有 projection_pending / stale_sources / draft_version 的实际含义，写出可实现的判定表。当前草稿的 freshness 不一定代表历史确认行，不直接套用。
- 明确允许为提示读取权威状态/版本元数据，但不得把实时来源、草稿、投影内容写进 Word。
- 服务端必须提供可靠的提示载体，前端必须展示；可替换具体响应头方案，但不可把提示行为写成可选。提示不阻断、不写入 Word 正文。

### 4. 澄清日计划缺项确认的跨请求竞态

区分两件事：同一请求的一致版本读取，与两次请求之间的确认对象是否变化。

案例：第一次 409 提示缺目标，另一人保存新版本且活动过程也变空，用户以 ack_missing=true 重试。重算 facts 不能证明用户看过新增缺项，不能声称它自动防止确认绕过。

- 修正 §3.3 “无预检-下载竞态”的绝对表述。
- 查既有确认依据；若没有，明确列为待用户决定：A 宽泛确认重试时最新内容及其全部缺项；B 确认绑定已展示的版本/事实，相关变化时重新提示。
- 给两者的用户可见差异、推荐项和最晚决定时点；可推荐 B，但不要写成已经确认。
- 版本清单/指纹/令牌等仅作为候选工程机制，不新增表或实现。
- 不论选项，每次请求重新鉴权、服务端独立计算事实、不信任客户端 facts 的要求保留。
- 验证矩阵按待定选项分别描述预期，不能让“仅重算就通过”成为已确认验收标准。

### 5. 澄清确认快照与日历变化后的导出布局

- 核实“有效日历”是否已有明确的时间语义依据；区分已确认 Contract 与 I5 当前工程提案。
- 明确分析：确认后的周日从教学日变为休息日；休息日新增为教学日；学期边界变化。当前列集合与旧快照不一致时，会不会遗漏已确认内容、把假期当教学内容或反之。
- 如果已有已确认规则能推出结果，引用来源并收敛；否则将确认时日历/导出时当前日历及变更后内容处理列为待确认项，不替用户选择。
- 不为解决问题修改确认表、增加迁移、扩展日历维护业务或重开系统架构。
- 单独补充可直接确定的工程不变量：一次导出中的范围选择、钉住版本、日历修订、列和表头来自同一一致性视图；维持只读，不加 FOR UPDATE。只规定需要验证的事务语义，不宣称 mock 测试已经证明 MySQL 隔离性。
