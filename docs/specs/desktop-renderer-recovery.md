# 桌面异常页面：明确确认后重开已保存档案

更新：2026-11-04。用户已明确选择“采用此手动恢复方案”：原生事件确认渲染器／浏览器异常退出后，提示未保存输入可能丢失，由用户点击重新打开最后保存的档案；保全任务回执，不自动重发AI、采用或确认；保存／恢复／任务不能安全收束时保留故障窗口与证据。该决定在本轮已生效，不再重复索取同一产品确认。

本规格补充[正常保存关闭合同](desktop-manual-daily-plan.md)，不改变其保存ack、30秒取消和最终放行语义。实现与证据归[生命周期核查](../bootstrap/desktop-renderer-lifecycle-review.md)，唯一执行入口为[current](../tasks/current.md)。本片沿现有pywebview／WebView2、本机服务、SQLite与宿主生命周期边界实现，不增加依赖、迁移或一级架构变化。

## 1. 触发与可见行为

- 仅当前窗口所属CoreWebView2的`ProcessFailed`明确报告`RenderProcessExited`或`BrowserProcessExited`时，登记主页面异常。环境的正常BrowserProcessExited、GPU／子帧退出、短时JS卡顿、单次脚本超时、截图失败和窗口被遮挡不触发此入口。
- 原生事件处理不得等待JS、数据库、网络或用户对话框。窗口／控件初始化与事件订阅在UI线程完成，失败只保留安全诊断，不把未知状态冒称已确认异常。不得修改安装的pywebview或系统保护。
- 提示和按钮独立于失效页面：说明“页面已停止，未保存的输入可能丢失”，提供“重新打开最后保存的档案”和“保留当前窗口”。显示用户文案，不展示内部路径、token、堆栈或供应商凭据。
- 不自动重载、创建新窗口、关闭旧窗口或重新发送业务。保留为默认焦点／默认Enter动作；主动选择或点击重开才接受输入丢失风险，Escape／X／关闭提示均等同保留。重复故障事件按精确窗口／代际去重；不反复弹窗。保留后允许用户再次从故障窗口的原生关闭动作明确打开同一选择，不能把该动作直接当作重开同意或正常保存ack。
- 主页面异常可冻结该窗口所属执行器的新claim／SEND，并暂停其周导出；使用独立owner，普通关闭取消不能解除故障冻结。在途结果仍可按现有发送确定性规则落回执，不能因页面丢失删除任务、候选或历史。

## 2. 手动重开与保全顺序

1. 明确点击重开后，核请求仍属于当前窗口、host、runtime和lifecycle bundle，且只有一个重开在途。旧窗口迟到事件、旧提示按钮或恢复替换后的回调不得操作新代际。
2. 使用现有数据根维护意向／写入计数及实际宿主工作状态阻止新写入，检查已接受数据库／原生文件保存、Word／导出、更新安装、备份恢复和AI持久化。不能将缺失JS响应、过时page_busy或探测异常解释为空闲；不能为了重开清掉busy或ack。
3. 发送中、结果待落盘、worker退出未确认、维护已有owner或保存状态不确定时，提示暂不能安全重开，保留故障窗口、原数据与回执。可以等待已接受工作自然完成后由用户再次明确尝试；没有自动重试、强杀或强制停止在途AI。
4. 只有在确认安全静止后，退休旧host／本机传输，确认旧服务和执行器停止；继续持有同一数据根锁。执行器必须在claim交接的同一gate内原子核定完整idle并置停止；只读`active_snapshot`／`is_snapshot_idle`不足以排除已离开gate但尚未设置active的claim。静止门不满足即拒绝，不调用可能触发worker终止的drain／dispose或以stop间接取消在途工作。没有确认停止不得关闭engine、释放根锁或开放新服务。与普通关闭不同，本次对已丢失未保存输入的接受来自原生明确选择，不伪造页面保存ack。
5. 复用已验证的engine／窗口代际机制打开同一已保存数据库；不做业务文件替换、备份恢复、导入或迁移。需要重新打开engine时旧Session与旧engine必须失效，保持原数据根锁，不能复用旧服务token／host页面票据／launch／采用或预览票据。
6. 新服务／host／窗口读取真实业务完成后，才能通过只绑定旧窗口的退休路径销毁旧窗。新窗口拥有新的故障观察与正常关闭协议。后续进程退出只清理最新bundle，不释放仍被旧服务或未确认worker使用的资源。
7. 新执行器只按现有冷启动规则分类并读取回执：已成功保留，已发送未明保持unknown，未发送可保持paused；重开不新增task／execution／attempt或自动发送，不自动采用／确认。新窗口显示已保存资料，不承诺恢复失效renderer内存。

安全检查前失败保持旧现场；原子idle门拒绝时不得提前封死旧host，应释放本次维护意向，让已接受工作自然完成后仍可明确重试。旧侧封锁／服务停止开始后，停止或engine关闭未确认时须继续持有独占写门和根锁，不能重新开放旧服务写入。

新执行器启动、app／host／service构造中途失败，也必须保留已创建资源的所有权。只允许独立freeze owner及原子idle-stop确认清理；未确认的部分bundle或CAS未安装资源阻止根锁释放，不调用dispose／drain／强杀。新窗口已经业务ready后仅旧窗口销毁失败，应保留可用的新工作台及旧现场，返回准确的旧窗保留状态，不销毁新窗口或自动创建第三个窗口。

退休或新服务建立后失败要明确保留锁和最新资源所有权，不能声称已还原正常、已正常关闭或数据未发生任何维护写入。只显示固定安全原因；不靠连续重开掩盖首失败。

## 3. 核查与交付要求

原生适配与业务协调器可按互斥文件并行。原生适配模块`desktop/renderer_recovery_native.py`仅提供以下宿主私有接口，业务重开、engine／服务／维护与发送权不交给它：

- `install_renderer_watcher(window, on_failure, *, log=None)`返回可幂等`close()`的观察器；只报告两个致命kind字符串。记录／回调不得等待JS／业务；原生UI线程与初始化／关闭解绑由适配器负责。
- `prompt_reopen(window) -> bool`供协调器的后台工作调用，安全调度原生UI；只有明确点击重开返回true，保留／X／错误均为false。按钮文字依§1。
- `notify_reopen_blocked(window, code) -> None`仅将审定的安全原因枚举映射为固定用户文案；不回显异常、路径或凭据。

现有原B只写该模块及`desktop/tests/test_renderer_recovery_native.py`，原A写审定的协调器与接线，不交叉改文件；Codex负责接口裁定与统一审阅。原生模块不新增公开JS桥接能力、正常运行调试开关或付费调用。具体A文件清单在技术方案核定后写入current。
