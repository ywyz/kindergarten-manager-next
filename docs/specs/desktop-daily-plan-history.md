## 1. 范围与阶段边界

本片交付同一份有效日计划的历史版本列表、只读历史内容、与当前已保存内容比较，以及教师确认后的整份恢复。它服务于误改后找回此前内容；第一版不做逐字段恢复。

恢复对象是一份计划的内容快照，不是整个数据库。删除记录找回、跨日期复制、历史版本直接导出、WebDAV备份／换机接续、安装升级、签名和游戏观察记录另行分片。现有历史不自动清理或压缩。

D2状态保持：[G17结果§7–10](../bootstrap/desktop-d2-g17-result.md#10-暂停签名转入d3-a设计2026-10-23)记录新A已采用保存v6，新B因教师话语问题未采用，新C未发起；适龄r3源码限定验证通过，新包在启动前被SAC以4551拦截。D3-A的设计及后续源码／隔离验证可以独立推进，不因此把D2、冻结包、真实AI或发行记为通过。

## 3. 教师使用流程

1. 已有日计划编辑页提供“历史记录”。先收口IME输入、保存当前未保存正文并确认编辑器仍干净，成功后再打开历史；无修改不新增版本。保存失败、结果不明或期间有新输入则留页保留输入。当前只有一个版本也可查看；不从空日期自动创建计划。旧学期、移出学期范围或改成停课日的已有计划遵守既有可编辑规则。
2. 按内容版本从新到旧列出保存时间、版本、当前标记；能证实为恢复的条目标注“从vN恢复”。普通旧版本以“保存记录”显示，不推断为手工或某次AI生成。默认50项、上限200项，按版本游标继续加载；新保存不会造成重复页或丢页。
3. 选中历史版本只读查看完整原文及各活动板块。保留编号、换行、空栏目和顺序。与当前已保存版本并列比较，以板块变化、增加／移除／替换提示帮助判断，不显示数据库JSON或内部身份ID。
4. 比较明确标注“当前已保存vM”和“历史vN”。拆分基准变化单独说明其对Word标红比较的影响，可展开查看；不把恢复预览的差异颜色等同Word标红规则。
5. “恢复此版本”进入明确确认：恢复整份内容，保留原日期及表头，当前vM仍留在历史，恢复后保存为新版本。确认按钮为“恢复并保存”，取消关闭预览且不写库。没有预览编辑框，所以关闭只读历史不产生新的“未确认修改”阻塞。
6. 恢复成功后显示“已从vN恢复并保存为vK”，回到当前编辑内容；历史列表保留vM、vN和vK。当前版本的恢复按钮禁用，服务端也明确拒绝来源等于当前版本的恢复预览／新请求，不产生成功回执或新记录；选择其他历史版本，即使可见文字相同，也按明确恢复动作新增版本，来源变化仍可追溯。
7. 成功响应返回后若页面已切换计划或出现新的输入，不覆盖编辑器。按已有冲突处理展示服务端结果，保留新输入；不能用迟到回执把页面回退到较早版本。

未保存正文、IME组合输入、候选预览草稿、保存中、结果待核对和关窗冻结，复用D1／D2的状态保护。候选草稿继续由候选自身的“采用并保存／取消编辑”处理；历史预览不暗中采用或清掉候选草稿。恢复请求在途或结果不明时，阻止同一页面再发恢复／保存覆盖操作；先查询该次回执。已有AI任务按原生命周期继续，不由历史界面停止或重发。

## 4. 恢复数据的完整边界

| 数据 | 恢复动作 |
| --- | --- |
| `raw_lesson_plan` | 从服务端选定历史内容原样复制；不重拆分、不替换成最新可编辑原文 |
| `adopted_content` | 整体复制全部板块，含反思、空值、数组顺序、组／游戏身份；不按当前设置补写 |
| `split_baseline`及`baseline_candidate_id` | 从选定历史继承，并验证同计划、内容版本、来源候选链及原始过程一致；历史无基准则恢复为无基准 |
| 当前计划指针 | 追加新内容ID、版本为当前版本+1，再原子更新当前指针 |
| 新版本编辑者／时间 | 当前本地档案、实际恢复时间；不伪造为历史编辑时间 |
| 历史来源 | 新增恢复记录，绑定恢复前、来源和结果三个内容版本；可回溯原AI采用记录 |
| 原AI采用记录 | 原记录保持；新版本不是一次新的AI采用，不复制旧`adopted_candidate_id/selected_targets_json/adopted_payload_hash`冒充本次采用 |
| 计划身份、表头、配置、任务、凭据 | 不回退、不重新执行，不从历史内容复制这些对象 |

新版本需要正常的AI provenance行：继承合法`baseline_candidate_id`，`adopted_candidate_id=null`、`selected_targets_json={}`、`adopted_payload_hash=null`；恢复来源通过独立恢复记录表示。恢复无基准的D1历史后可正常保存和导出，不标红；有基准时继续按原基准与恢复后最终过程比较。

组／游戏ID只能从服务端已验证的同计划历史快照读取，允许重新出现当前版本已经移除的历史身份；不得接受客户端任意身份。校验整个快照的结构及身份唯一性，不为了通过当前版本的ID白名单而重新分配历史ID。普通手工保存仍沿用原有身份约束。

历史基准验证采用其原候选契约和不可变来源链，不要求旧记录符合当前最新指导修订。损坏、跨计划、缺失来源或不支持的格式必须明确报错且不写库，不静默清空基准或截断内容。读取失败不能显示为空历史并让教师覆盖。

## 5. 本机接口与事务设计

所有接口沿用现有应用会话、Host／Origin、本地档案及当前班级校验，输入`extra=forbid`。历史版本必须属于URL所指有效计划；软删除或错归属返回不存在，不借历史接口恢复删除记录。日期资格只用于新建，不重新限制已有计划的内容恢复。

| 接口 | 契约 |
| --- | --- |
| `GET /api/daily-plans/{id}/history?limit=50&before_version=...` | 只读列表，版本降序；返回条目、当前版本及下一页游标，历史内容不内嵌全量正文 |
| `GET /api/daily-plans/{id}/history/{version}` | 一致读事务内取得该历史内容、计划固定表头和可证实的恢复来源；不冒充当前版本DTO |
| `POST /api/daily-plans/{id}/history/preview-restore` | 严格正整数`source_content_version,expected_content_version`；服务端读取两份快照，返回比较材料及预览凭证，不持久化业务变更 |
| `POST /api/daily-plans/{id}/history/restore` | `request_id,preview_token,expected_content_version`；不接收客户端正文、基准或来源ID；成功回执给出来源、恢复前、结果版本及内容ID |
| `GET /api/daily-plans/{id}/history/restore-operations/{request_id}` | 只读查询本档案、本计划的该次恢复回执；不存在或查询失败不自动重发 |

预览凭证参考既有采用凭证的10分钟、启动代次和有界内存设计，绑定当前应用会话范围、档案、计划、来源内容ID／版本／快照摘要、当前内容ID／版本／摘要；使用独立操作域，不能跨应用会话使用，也不能把AI采用凭证用于历史恢复。重启或过期后须重新预览；已提交操作优先读回执，不因旧token失效重复恢复。

恢复在一个`BEGIN IMMEDIATE`短写事务内：先核对幂等回执，再重读当前指针和来源，校验预览事实及内容，追加新内容／基准关联／恢复记录，条件更新当前内容ID和版本，写`restore_daily_plan`操作审计并提交。任何一步失败全部回滚；成功只以COMMIT为准。用户等待、比较渲染及网络等待不在写锁中。

恢复记录同时承载持久回执，新增`local_daily_plan_restores`表：本地档案、request_id及规范请求指纹、计划ID、来源内容ID／版本、恢复前内容ID／版本、结果内容ID／版本、创建时间。约束包括`(profile_id,request_id)`唯一、结果内容ID唯一，三个内容引用均以同计划的复合FK约束；历史来源不可跨计划。实际增量迁移为`20261023_0005_local_history`，细节见[实现结果](../bootstrap/desktop-d3-history-result.md)。

同键同请求返回原恢复结果；同键异请求拒绝，不能再增加版本。结果不明时前端保留完整原请求，只查询回执，不换键重发。回执指向当时结果；读回后还要查询当前计划，避免后续已保存vK+1却被回执vK覆盖。恢复回执属于非AI操作域，不污染现有AI操作计数或假称AI请求。

采用增量Alembic迁移；旧内容、旧provenance及原AI回执不改写，不为旧版本伪造恢复事件。新增表和约束需要从现有D1／D2合成库升级及重启验证，禁止把真实教师库作为迁移试验。原有Word生成及候选写入链不为本片改版。

## 6. AI并行与候选有效性

恢复不创建、恢复执行或重试AI任务，不触碰密钥。已有在途结果按现有逻辑落为候选，不能直接改正文；发送前的原任务仍按真实业务输入依赖复核。

恢复会推进内容版本，因此恢复前取得的采用预览不可直接提交。候选能否再次采用，仍按当前业务输入／目标／基准关系复核，不把“内容版本改变”当作所有候选永久失效的充分条件。若恢复使实际依赖重新一致，原候选可重新预览并由教师明确采用；不因为查看历史自动发出新请求。

- `backend/app/local/models.py`：`LocalDailyPlanContent`已经是追加式版本；`LocalDailyPlanAIProvenance`、`LocalOperationRecord`分别保存来源与操作事实。已核查的本地API尚无本片历史恢复接口。
- `backend/app/local/daily_plan_service.py`：`save`沿用当前拆分基准，组／游戏ID也以当前版本为允许集合；不能把旧内容交给普通PATCH就宣称完整恢复。应新增专门服务，抽取必要共用校验时保持原保存语义。
- `backend/app/local/ai_provenance.py`：`resolve_baseline`验证选定内容的基准及同计划候选链，可作为历史基准校验依据；它不等于完整历史恢复服务。
- `backend/app/local/ai_adoption.py`与`ai_inputs.py`：预览版本保护、业务依赖复核和幂等顺序可参考；不把恢复实现成一次伪造AI采用。
